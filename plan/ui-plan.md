# UI plan

The platform UI for the Lead Gen Engine. Planned 11 Sep 2026.
Master plan: [../PLAN.md](../PLAN.md) · Engine spec: [../context/INDEX.md](../context/INDEX.md)

---

## What the UI is for

The engine already acquires, qualifies, detects pain and drafts emails. It runs from a CLI. The
UI gives four groups of people the four things they cannot do from a terminal:

| Who | Daily question | Screen |
|---|---|---|
| **Sales / SDR** | Who do I contact today, and what exactly do I say? | Today · Leads · Lead detail |
| **Ops / data lead** | Which of the machine's judgements need a human? | Review queues · Hand-check |
| **Ops / data lead** | Why is this firm in this tier? | Firm detail — provenance |
| **Admin / builder** | Is the pipeline healthy, and what is it costing? | Pipeline · Settings |

### The one reason the UI matters strategically

**It is the place where outcomes get recorded.** Sending happens outside this system, so nothing
tells the engine which leads replied or closed. Without that, the attribution join never runs:

```
outcome × signal kind × tier      -- joined on lead.arming_signal
```

and every scoring weight in the spec stays a seeded guess forever. A "Replied / Meeting / Won /
Lost / Not now" button on each lead is the cheapest way to close that loop, and it is not
possible from a CSV.

## Two repos

| Repo | Contains | Location |
|---|---|---|
| **backend** | The pipeline (all planes, SQL, configs, journey copy), **a new FastAPI layer**, the knowledge base (`context/`) and plans | **This folder** — already a git repo; the portable Postgres, the venv and the data live here |
| **frontend** | The web app | New sibling repo: `C:\Users\ACER\Desktop\lead-gen-web` (no spaces: Node tooling breaks on them) |

**The contract between them is an OpenAPI document** generated by the backend and checked into
it. The frontend generates its TypeScript types from it, and its CI fails when the contract
drifts. No business rule is ever implemented twice: the frontend never re-computes a tier, a
list-hygiene filter or a draft. It asks the API, which calls the same code the CLI does.

### When to split

**Not now.** The live probe is crawling 242 firms from this folder; moving the venv or the
database under it would break the run.

**Right after the probe completes and its results are verified.** In this order:

1. Probe finishes, and the ranked list and drafts are reviewed
2. **Backend: first commit** — a snapshot of a working, tested engine (~800 tests)
3. Backend: FastAPI layer + `openapi.json` (UI-0)
4. **Frontend: create the repo**, scaffold it, run the native-binary smoke test (see Risks)
5. Frontend: first screen (UI-1)

The API contract must exist before the first line of frontend code. That fixes the order.

**GitHub:** `gh` is installed but not logged in. Local repos need nothing more. Remote repos need
you to run `gh auth login` and say which account or org and whether they are private.

## Stack

| Layer | Choice | Why |
|---|---|---|
| API | **FastAPI** + uvicorn (plain, no `[standard]` extras) | Python already; pydantic already used by the extraction contract. The `[standard]` extras pull compiled modules this machine's Application Control may block |
| Contract | OpenAPI 3.1 → **openapi-typescript** | Generated types, drift caught in CI |
| Frontend | **Next.js (App Router) + TypeScript** | Matches the team's frontend tooling; Auth.js makes Google Workspace sign-in straightforward when it is hosted |
| UI kit | **Tailwind + shadcn/ui** (Radix) | Accessible primitives, no design-system build-out |
| Data | **TanStack Query** + **TanStack Table** | Server state and dense, sortable, filterable tables — most of this app is tables |
| Forms | react-hook-form + zod | Review decisions, outcomes, uploads |
| Tests | Vitest + Testing Library | Browser-driver downloads are likely blocked on this machine |

**Provisional until the scaffold smoke test.** See Risks: native Node addons may be blocked here
the way selectolax and uv's Python were.

## Screens

### Today — `/`

The SDR's first screen. It answers "what must happen today", not "what happened".

- **STRIKE leads.** High intent, low contest, so a human writes these the same day. Each shows the
  pain sentence verbatim, how long ago *we* first saw it, and the decision-maker. The clock is
  visible: the spec's target is signal-to-contact under 48 hours.
- **Needs attention:** firing alerts, alerts with `no_data` (shown distinctly — absence of data is
  information), review-queue counts, and bench status. An empty bench is shown as "leads cannot be
  armed", because invariant I4 blocks arming without inventory.

### Leads — `/leads`

```
┌ Leads ─────────────────────────────────────────────────────────────────────┐
│ [STRIKE 12] [SEQUENCE 184] [NURTURE 406] [Phone list 91] [Excluded 1,204]  │
│ Tier ▾  Metro ▾  Pain ▾  Contest ▾  Email verified ▾         [Export CSV]  │
├────────────────────────────────────────────────────────────────────────────┤
│ Firm                 Tier  Pain                                  Contest   │
│ Atlanta PI Law Grp   1A    Paralegal role open 26 days           HIGH  ▸   │
│                            "The attorneys at … work on a contingency…"     │
│ Contact: J. Gore — owner · email unverified (vendor: verified)             │
└────────────────────────────────────────────────────────────────────────────┘
```

- Bands are tabs. **Phone list** is grade B: named person, no verifiable email. It is a product,
  not a reject pile. **Excluded** shows every lead the hygiene filter removed and why (suppressed,
  portal track, DQ, unresolved token, no evidence). An exclusion you can explain is reusable.
- **Export CSV runs `build_list`**, so the hygiene filter applies at export time, every time. The
  UI never offers a static list, and grade B never reaches an email export.
- Email status is always explicit: *verified* · *unverified (vendor says verified)* · *catch-all —
  failure*. Nothing is silently treated as verified.

### Lead — `/leads/[id]`

```
┌ Atlanta Personal Injury Law Group · 1A · SEQUENCE ──── [Replied] [Not now ▾] │
│ Fit 41 · Intent 40 · Contest HIGH           (weights are seeded, unmeasured) │
├ Pain ───────────────────────────────────────────────────────────────────────┤
│ job_posting_open · Paralegal · first seen by us 14 Aug (26 days)             │
│ "…" — careers page, 2 sources, reposted once                                 │
├ People ─────────────────────────────────────────────────────────────────────┤
│ J. Gore — owner (site) · j.gore@… unverified   │  Office manager — none found │
├ Drafts ──────────────────────────────── day 0 · 3 · 7 · 10 · 14 · 18 · 21 · 25 · 28 │
│ Touch 1 — "your paralegal opening"                                  [Copy]   │
├ Timeline ───────────────────────────────────────────────────────────────────┤
│ DISCOVERED → PROFILING → CLASSIFIED → CONTACT_PENDING → RESOLVED            │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **Pain first**, because it is the reason the lead exists and the first line of the email.
- **Score breakdown** lists each fit term and each signal's weight × decay. It is labelled as
  seeded, because the spec says it is.
- **People** shows owner *and* administrator, since the spec says to capture both, and marks
  which one is missing.
- **Drafts** shows all 9 rendered touches with copy buttons. Touches that were skipped say why
  (e.g. "touch 8 omitted — the posting closed").
- **Outcome actions** (Sent · Replied · Meeting · Won · Lost · Not now until *date* · Opt-out) are
  lifecycle transitions. The database enforces them, and the event log records who and when.
  **Opt-out suppresses the whole domain**, needs confirmation, and only an admin can reverse it.

### Firm — `/firms/[id]` — "why this tier?"

Every resolved value, with the claim that won and the claims that lost:

```
fee_model   contingency    ← regex:p6  0.95  "…work on a contingency fee basis…"   [page ↗]
                              llm:p8:v2 0.80  contingency                            agrees
primary     personal_injury ← rules:practice 0.63 · vendor hint: personal_injury     agrees
attorneys   unknown        — no team page found (not guessed)
tier        1A             = fee_model ∈ {contingency} ∧ practice = personal_injury
```

`unknown` is shown as **"unknown — not guessed"**, never as a blank. The spec's whole design turns
blank-looking failures into visible ones. The page also shows the crawled documents (page kind,
status, robots decision), signals, contacts, merge aliases and lifecycle.

### Review queues — `/review/*`

Keyboard-first triage: `j`/`k` to move, `1`/`2`/`3` to decide, `u` to undo. Every decision is
written to an audit table with reviewer and time.

| Queue | Shows | Decisions |
|---|---|---|
| **Hand-check (G2)** — build first | 50 probe firms × every attribute, each value with its evidence | ✓ correct · ✗ wrong (+ the right value) → per-attribute accuracy; the gate's status |
| **Conflicts** | The disagreeing claims side by side, with evidence | Accept one · send to P9 · mark unknown |
| **Identity** | Two near-duplicate records side by side | Merge · keep separate |
| **Agency** | Rejected postings grouped by company and rule | Confirm agency (extend blocklist) · real firm (allowlist) |
| **Discovery** | Companies from postings that match no firm | Find or add the firm |

**Hand-check comes first because it is a gate:** nothing widens beyond the probe until 50 records
are accurate on every attribute, and today there is no tool to do that check.

### Journey — `/journey`

The 9-touch timeline; templates by touch, variant and tier; a **preview against a real lead**;
and the live guard rails the renderer enforces — banned framing, the tier-4 paralegal ban,
unresolved tokens. v1 is read-only. Editing copy from the UI needs templates moved from files into
a versioned table; that is a later decision.

### Pipeline — `/pipeline`

Flows with per-step status; component runs (from `task_run` and run notes); gates (invariants,
G1, G3, G7) with their reports; alerts (ok · firing · no_data); the source registry (robots
state, crawl-delay, last checked); LLM spend from `llm_call`. **v1 is read-only.** Triggering
live crawls from a web button is deliberately left out — runs go through the CLI and the
scheduler.

### Settings — `/settings`

- **Suppression:** upload the customer list (CSV of domains → `suppression_load`); list entries
  with their reason. Removal is admin-only and needs a reason. Suppression is sticky by spec.
- **Bench inventory:** an editable table → `bench_sync`, until portal access exists.
- **Providers:** OpenRouter, email verification and Places each shown as *configured* or *inert*.
  **Key values are never displayed or sent to the browser.**
- **Crawler identity:** the User-Agent in use.

## API (backend repo, `lge/api/`)

The API is one more client of the store. Writes go through the same `writer()` / `lifecycle()`
contexts as the pipeline, so every database invariant still holds, and rules are reused rather
than re-implemented (`build_list`, `build_journey`, `reconcile`).

```
GET  /api/today
GET  /api/leads?band=&tier=&metro=&signal=&contest=&verified=&cursor=
GET  /api/leads/{id}                      firm · score breakdown · signal · contacts · timeline
GET  /api/leads/{id}/drafts               rendered 9-touch journey
POST /api/leads/{id}/outcome              {action, until?, note} → lifecycle transition
GET  /api/leads/export.csv                runs build_list — hygiene at export time
GET  /api/firms?q=&tier=&state=&cursor=
GET  /api/firms/{id}                      attributes + winning/losing claims · documents · aliases
GET  /api/review/{queue}                  handcheck | conflicts | identity | agency | discovery
POST /api/review/{queue}/{item}/decision
GET  /api/pipeline/{flows|runs|gates|alerts|sources|costs}
GET  /api/suppression    POST /api/suppression/upload
GET  /api/bench          PUT  /api/bench
GET  /api/journey/templates    POST /api/journey/preview {lead_id}
GET  /api/meta/providers                  booleans only — never key values
GET  /api/reports/{coverage|attribution}
```

New tables: `handcheck_result` (firm, attribute, reviewer, correct, corrected value, time),
`review_decision` (the audit of every queue decision), and later `app_user` / roles.

## UX rules taken straight from the spec

| Spec principle | UI rule |
|---|---|
| Every value traces to a claim | Every attribute shows its source and evidence on hover or expand |
| `unknown` is first-class | Say "unknown — not guessed". Never a blank, a dash or a zero |
| `no_data` ≠ ok ≠ firing | Three visually distinct alert states |
| Weights are seeded | Label score breakdowns "seeded — to be replaced by measured outcomes" |
| Grade B is a product | Phone list is its own tab, not a filter state of Excluded |
| Suppression is sticky | Confirmation plus a reason to add; admin plus a reason to remove; both audited |
| Capacity, never replacement | The journey preview runs the banned-framing guard live |
| Evidence is the first line | The pain sentence is the most prominent text on a lead |

## Security and data

The contacts table holds names, emails and phones of real attorneys.

- **Until UI-7 the API binds to `127.0.0.1` only.** Not reachable from the network, no public
  URL.
- **Before any hosting:** Google Workspace sign-in restricted to `legalsoft.com`; roles (viewer,
  SDR, ops, admin); every CSV export audited with who, when and how many rows.
- Provider keys stay server-side. The browser learns only whether each one is configured.

## Risks

| Risk | Why | Mitigation |
|---|---|---|
| **Native Node addons blocked** | Windows Application Control on this machine already blocked selectolax and uv's Python. Next.js (SWC, Turbopack), Tailwind v4 (oxide, lightningcss) and esbuild all ship unsigned native binaries | A smoke test at scaffold time, before any feature work. Fallbacks: Next.js with webpack + the SWC wasm build; Tailwind v3 (pure-JS PostCSS) |
| Business rules duplicated in the frontend | The classic drift | The rule above: the API calls the pipeline's own functions; the frontend only renders |
| Outcome capture skipped as "nice to have" | It looks like a feature; it is the attribution mechanism | It is UI-3, ahead of the other review queues |
| Live crawls triggered from a web button | A misclick crawls hundreds of sites | Pipeline is read-only in v1; runs stay in the CLI and scheduler |
