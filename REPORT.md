# Development report

What was built, day by day, in plain words. Newest first.
One paragraph per day — enough that someone who has never seen the code knows what changed and why.

---

## 17 September 2026

We stopped and re-planned instead of building. Looking at the whole project from the top, most of the work is getting the data — reading a firm's website properly, searching the web for what the site doesn't say, and finding each person's LinkedIn profile — and the build so far had gone deep on the later steps (tiering, email drafts, screens) while those three stayed weak. The new plan puts them first, in order, each measured on the 242 test firms before it runs over all 22,000, and pushes the outreach writing to the end where it belongs. Three things were pinned down along the way: the sheet reader must never require a column — the AI reads whatever is uploaded and research fills the gaps; DuckDuckGo has to be replaced with a paid search engine because it blocks us after a few hundred queries (Serper recommended, about fifty dollars for the whole list); and the screens need to become something a team can log into and use, not a one-person project. The morning also had a self-inflicted outage — Postgres had been started inside a task that was later stopped, which took the database down and made every page return an error — fixed by starting the database and the engine detached from anything that can be stopped by accident. Then the first chunk of the new plan was built: uploading a sheet no longer assumes anything about its columns. The AI reads the header row and a dozen sample rows once, says which column is which and why, and its answer is checked against the actual values before it is trusted — a column it calls "email" whose cells are web addresses is overruled. The only things a sheet must have are a firm name and some way to reach the firm (a website, an email, or a location); size, practice, people and the rest are marked "filled by research" instead of "missing". The loader also stops reading whole sheets into memory: a 100,000-row file was read in under a second at 25 MB, in batches of 500, so the size of a sheet no longer matters. Every outside provider — the AI, the search engine, the email finder and verifier — is now chosen by one setting each, so switching Serper for Brave or Hunter for NeverBounce is a line in a config file, not a code change. The second chunk followed: the crawler now reads six kinds of page per firm — home, about, contact, the attorneys and team pages, testimonials, careers — instead of twelve kinds and thirty pages, and the list lives in one config file that every part of the engine asks, so adding a kind back is one line. On the 232 test firms that cut the pages read by nearly half while losing almost nothing: the number of firms whose size we know went up by half, because the attorneys a firm names on its own team page now count as its size (one firm was correctly ruled out for listing 51), practice areas and people found were unchanged, and five firms lost their fee-model reading because their "no fee unless we win" line only appeared on a practice page. Doing this uncovered a quiet bug worth more than the chunk itself: a fact read off a page fetched later — say a news page — kept counting as the freshest thing known about a firm even after the engine stopped reading that kind of page, so old readings could outlive their source. Now each reading pass replaces everything that pass said before about a firm, and 617 such leftover facts were cleared from the test firms. The third chunk put the web search behind one door: the engine that answers is chosen by which key is in the settings — Serper (Google's results) first, Brave as the fallback, DuckDuckGo only when there is no key — and every result, every claim and every logged query says which engine produced it. When the engine can look up a business listing directly, the Google Business Profile (rating, review count, phone, the listing itself) is read from that instead of guessed from snippets, and every search for a person now includes the firm's city so namesakes in other towns stop matching. It is built and tested against recorded answers; the first real run waits for the Serper key. The fourth chunk did the same for people's email addresses: Hunter is wired in as the service that finds a decision-maker's address from their name and the firm's domain, or finds the decision-makers themselves when the site named nobody, and as the service that checks whether an address is real — with NeverBounce kept as a one-line switch for the checking part. Hunter's own verdicts are translated onto our stricter scale (a "catch-all" domain counts as a failure, never a pass), a person is never paid for twice, and nothing runs until the Hunter key is in place.

## 16 September 2026

The "research this firm" buttons on the screen looked like they were working but nothing ever happened — the job was being handed to a worker before it had been saved, so the worker went looking for it, found nothing, and gave up silently. Jobs are now saved first and then run on their own thread, and anything left hanging from a crashed run is marked failed when the engine starts, so the screen never claims work is in progress when it isn't. We also changed how we look people up: instead of one search per person, we now run one search per firm and match every profile on the results page against the people we already know about, which takes the full list from roughly 250,000 searches down to about 30,000 — the difference between a run that gets us blocked and one that finishes. Finally the project was split into three repositories that all live inside the one Lead Gen Engine folder — the engine itself at the top, brain underneath it (the plans, the decisions and this report) and frontend beside it (the screens) — and the loose PDFs, superseded drafts and old run logs were cleared out of the code folder, so it is now obvious where anything lives without anything leaving the project folder.
